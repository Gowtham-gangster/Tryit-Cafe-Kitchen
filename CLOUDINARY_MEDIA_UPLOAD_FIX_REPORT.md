## 1. Executive Summary & Root Cause Analysis

### A. Root Cause of Upload Failure
When attempting to upload media via the Owner Dashboard, the frontend presented the error toast:
> *"Failed to upload image. You can also paste an image URL directly."*

Upon in-depth inspection and real server runtime tracing, **four cascading defects** were identified:

1. **Spring Boot Default Multipart File Limit (1MB) (Primary Failure):**
   - **Root Mechanism:** Spring Boot's embedded Tomcat defaults `spring.servlet.multipart.max-file-size` to `1MB` (1,048,576 bytes) and `max-request-size` to `10MB`. Real images taken on modern smartphones or cameras consistently exceed 1MB (typically 2MB–8MB).
   - **Runtime Evidence:** The server threw `org.apache.tomcat.util.http.fileupload.impl.FileSizeLimitExceededException: The field file exceeds its maximum permitted size of 1048576 bytes`.
   - **Exception Misclassification:** `GlobalExceptionHandler` did not catch `MaxUploadSizeExceededException`, causing Tomcat to return an unhandled `500 Internal Server Error`, triggering the frontend catch-all toast.

2. **Manual `Content-Type: multipart/form-data` Header Override:**
   - In `frontend/src/api/ownerApi.ts`, `uploadMedia` manually defined `headers: { 'Content-Type': 'multipart/form-data' }`.
   - By hardcoding this header without the multipart boundary string generated by the browser, Axios stripped the boundary delimiters, resulting in malformed multipart payloads when received by Spring Boot.

3. **Invalid Cloudinary Cloud Name in Environment Configuration:**
   - In `backend/.env`, `CLOUDINARY_CLOUD_NAME` was configured as `Root`.
   - **Runtime Tracing:** Real API call to Cloudinary returned `Invalid cloud_name Root` (Cloudinary cloud names are lowercase alphanumeric identifiers for product environments, not user labels or system keywords like "Root").

4. **Silent Local `/uploads` Fallback in Production:**
   - In `CloudinaryService.java`, when Cloudinary calls failed, the code caught the exception and silently redirected files to the local container/machine filesystem under `/uploads`, returning an HTTP 200 with a local URL (`http://localhost:8088/api/v1/public/media/...`).
   - In ephemeral containerized cloud environments (e.g., AWS ECS, Render, Railway, Kubernetes), local storage is wiped on restarts, leading to broken images and violating the production specification.

## 2. Architecture Overview

### A. Backend Media Upload Architecture
```
Owner React UI
  │
  ▼ multipart/form-data (file: MultipartFile, folder: String)
Spring Boot Gateway (/api/v1/owner/upload-media)
  │
  ├─► Security Filter Chain: Verified JWT & @PreAuthorize("hasRole('OWNER')")
  │
  ├─► Global Exception Handler: Intercepts MaxUploadSizeExceededException
  │
  ▼ CloudinaryService (Centralized Service)
  │
  ├─► Validation Layer:
  │     • Reject empty/null files
  │     • Sanitize original filename (block traversal `..`, `%`, null bytes)
  │     • Extension allowlist: JPG, PNG, WEBP, GIF (Images <= 10MB) | MP4, WEBM, MOV (Videos <= 50MB)
  │     • Content-Type inspection
  │     • Magic-Byte signature inspection (JPEG: FF D8 FF, PNG: 89 50 4E 47, WEBP: RIFF...WEBP, GIF: GIF8)
  │     • Controlled folder allowlist: dishes, menu, offers, gallery, hero, profile, categories
  │
  ├─► Cloudinary Java SDK (Authenticated Server-Side Upload):
  │     • Folder prefixed: tryit_cafe/{folder}
  │     • Auto optimization: quality=auto, fetch_format=auto, resource_type=auto
  │     • Fallback strictly disallowed in production (allow-local-fallback=false)
  │
  ▼ Response: { url: secure_url, publicId: public_id }
```

### B. Frontend Upload Architecture
```
Owner Pages (Menu / Offers / Gallery)
  │
  ▼ Client-Side Validation:
  │   • Size check (< 10MB for images, < 50MB for video)
  │   • Instant preview URL via URL.createObjectURL(file)
  │
  ▼ ownerApi.uploadMedia(file, folder)
  │   • Native FormData (file, folder)
  │   • Content-Type boundary managed automatically by Axios/browser
  │
  ▼ Dynamic Error Catching:
      • Displays exact server response (`err?.response?.data?.message`)
      • Safe, actionable guidance for administrators
```

## 6. Security & Credential Protection

- **Frontend Isolation:** `CLOUDINARY_API_SECRET` is strictly backend-only. Never exposed in React source, bundles, or client configurations.
- **Log Sanitization:** All Cloudinary error messages pass through `sanitizeCloudinaryError` so credentials and secrets are scrubbed before reaching logs or API responses.
- **Audience & Access Integrity:** Method-level `@PreAuthorize("hasRole('OWNER')")` guards ensure non-owners cannot upload or mutate cafe media.
